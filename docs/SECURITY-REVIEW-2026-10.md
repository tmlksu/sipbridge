## 1. システムと信頼境界

```
[Android アプリ] ──WSS──▶ [Cloudflare edge: TLS 終端 + Access 認証] ──Tunnel──▶ [cloudflared]
                                                                                   │ HTTP (loopback)
                                                                                   ▼
                                              [relay (Go)] ──SIP/RTP 平文 UDP (LAN)──▶ [Asterisk / HGW]
                                                   └──HTTPS──▶ [FCM (Google)] ──▶ 端末の起床
```

- **信頼境界** (trust boundary) = データや制御が、信頼の度合いが違う領域をまたぐ場所。
  脅威モデリングはここを列挙することから始まる。このシステムの主な境界:
  1. インターネット ↔ Cloudflare (Access で認証)
  2. Cloudflare ↔ relay (JWT を relay で再検証)
  3. WS クライアント ↔ relay 内部の権限 (どの端末がどの内線を使えるか)
  4. relay ↔ LAN (SIP/RTP は平文 UDP、送信元は偽装可能)
  5. 同一端末上の他アプリ ↔ Android アプリ (exported component、ストレージ)
- 今回の issue は、ほぼ全てが「どこかの境界で、相手を信じすぎていた」ものとして説明できる。

## 2. 使う体系 (フレームワーク) の要点

| 体系 | 何のためのものか | 今回の使いどころ |
|---|---|---|
| **CIA** (機密性・完全性・可用性) | 守る性質の分類 | 対策が可用性を損なう失敗 (§4) の理解 |
| **STRIDE** (なりすまし・改ざん・否認・情報漏洩・DoS・権限昇格) | 脅威の網羅的な洗い出し | 各 issue の分類 (§3 の表) |
| **多層防御** (defense in depth) | 1 つの対策が破られても次で止める | CF Access + JWT 再検証 + 端末 ID 固定 + SIP パスワード |
| **最小権限** (least privilege) | 必要な権限だけ与える | Android 権限削除、コンテナの cap_drop、Asterisk の発信 context |
| **フェイルセキュア** (fail securely) | 失敗時に安全側へ倒す | 暗号化ストア失敗時の扱い (#42)、設定ガード (#37) |
| **正規化してから検証** (canonicalize then validate) | 表現揺れによる検証すり抜けを防ぐ | 発信先の percent-decode → 許可リスト照合 (#32) |
| **許可リスト** (allowlist) > 拒否リスト | 知らない入力を既定で拒否 | 発信先・内線名・端末 ID の形式 |
| **OWASP MASVS v2** | モバイルアプリの検証標準 | STORAGE / NETWORK / PLATFORM の各項目 |
| **OWASP API Security Top 10 (2023)** | API 特有の弱点 | API2 (認証の不備), API4 (無制限なリソース消費) |
| **CWE** | 弱点の共通の名前 | 各 issue の根本原因の名前づけ |
| **RFC 8725** (JWT BCP) | JWT を安全に使うための現行の推奨 | alg 固定・iss/aud/exp の検証 (#36) |
| **ゼロトラスト** (NIST SP 800-207) | ネットワーク上の位置を信頼の根拠にしない | LAN からの SIP を無条件に信じない (#28) |
| **残存リスクの受容** (risk acceptance) | 直さない判断を明示して記録する | #44 #45、`docs/SECURITY.md` §8 |

## 3. issue ごとの解説

コードの場所は `security-fixes` ブランチ基準。

### 3.1 relay: LAN 側

**#28 SIP の送信元を検証していなかった / #29 RTP の送信元を検証していなかった**
- 攻撃: 同じ LAN の機器が偽の INVITE を送ると、任意の番号・表示名でアプリが鳴る (着信の詐称)。
  通話の識別子を盗聴できれば BYE で切断もできる。RTP なら通話に音声を差し込める。
- 根本原因: UDP を `0.0.0.0` / `[::]` で待ち受け、届いたものを無条件に処理していた。
  「LAN の中だから安全」という暗黙の前提 = ゼロトラストの逆。
- 対策: SIP サーバとみなせる送信元 IP 以外からの**要求**を無応答で破棄する (応答はトランザクション照合で
  守られるので通す)。RTP は SDP の宛先 IP と信頼集合で照合する (ポートは NAT でずれるので見ない)。
  - `relay/internal/sipbackend/trust.go` (信頼集合), `backend.go` (sipgo の読み取りフィルタ), `rtp.go`
  - 実装の落とし穴: 受信ソケットが「待受」と「REGISTER 送信用」の 2 本あり、ハンドラ側で見るだけでは
    CANCEL/ACK やコネクションプール登録が素通りする。ライブラリの受信経路の最下層で掛ける必要があった。
- 位置づけ: STRIDE の Spoofing / Tampering。CWE-290 (なりすましによる認証回避), CWE-346 (送信元の検証不備)。
- **限界 (重要)**: UDP の送信元は偽装できるので、これは**認証ではない**。多層防御の 1 層にすぎない。
  本当に防ぐには SIP over TLS + SRTP (RFC 5630, RFC 3711) か、VLAN での分離が必要 (#35)。

**#32 発信先 `dial.to` を検証していなかった**
- 攻撃: `to` に改行 (CRLF) を混ぜると、SIP メッセージに任意のヘッダ (例 `Replaces:`) を差し込めた
  (sipgo は URI の user 部をエスケープせず書き出す)。また、任意の宛先に発信できるので、外線に出られる
  設定なら**トールフロード** (不正な国際・高額発信) の踏み台になる。
- 対策: percent-decode と全角→半角の正規化をしてから、電話番号 (`+0-9*#`) か英数字の user 名だけを許す。
  内線名 (`sip_account.user`) と表示名も検証・エスケープする。
  - `relay/internal/sipbackend/validate.go`, `validate_test.go`
- 位置づけ: CWE-93 (CRLF 注入), CWE-20 (入力検証の不備)。「正規化してから検証」しないと二重エンコード
  (`%250D`) ですり抜ける (CWE-174)。許可リスト方式。
- 最小権限: 発信できる宛先の制限は relay ではなく **Asterisk の dialplan (context)** の責務。
  relay が見るのは形式の妥当性だけ、と責任を分けている。

### 3.2 relay: 認証・認可

**#36 JWT の iss を検証していなかった (と、exp の無い JWT も通っていた)**
- JWT の署名が正しくても、「誰が発行したか (iss)」「誰宛てか (aud)」「いつまで有効か (exp)」を確かめないと、
  別の文脈で発行されたトークンを受け入れうる。golang-jwt v5 は `WithExpirationRequired` を付けないと
  exp の**無い**トークンを期限切れにしない (ライブラリの既定値を信用しない教訓)。
- 対策: RS256 固定、aud・iss・exp を必須に。認証の主体 (principal) を `sub:` / `cn:` 付きでログに出す。
  - `relay/internal/auth/auth.go`
- 位置づけ: RFC 8725 (JWT BCP) §3.1 アルゴリズム検証, §3.8〜3.9 iss/aud。CWE-347。
  OWASP API2:2023 (Broken Authentication)。ログに主体を残すのは「否認 (Repudiation)」対策と、
  漏洩時の調査・失効判断のため。

**#31 X-Device-Id を自称だけで信じていた**
- 攻撃: CF Access の Service Token が漏れると、観測した端末 ID を名乗るだけで、その端末の内線を使い、
  本物を切断できた。
- 対策: 端末 ID を、最初に使った認証主体 (principal) に結び付ける TOFU (Trust On First Use)。
  SSH の `known_hosts` と同じ考え方。`DEVICE_BINDING=off|warn|enforce`。
  - `relay/internal/session/limits.go`, `relay/internal/state/state.go`
- 学びどころ: **共有クレデンシャルは帰属 (attribution) を壊す**。全端末で 1 本の Service Token を
  共有していると、principal が全員同じなので、この対策は何も守れない。端末ごとに発行して初めて効く。
  TOFU の弱点 (最初の 1 回を攻撃者に取られると逆に固定される) も併せて理解する。

**#30 上限・レート制限が無かった (+ 監査で見つかった乗っ取り)**
- 攻撃: 1 本の接続でパスワードを毎秒約 14,000 回試せた。任意の数の内線を作らせ、それぞれが Asterisk へ
  REGISTER を打ち続けた (relay を踏み台にした総当たり、リソース枯渇、SD カードへの書き込み)。
- 追加で見つかった論理的な欠陥: 内線が未登録の間 (Asterisk 再起動中など) は、誤ったパスワードでも
  結び付けが受理され、正規の端末が戻った後も残っていた。**状態遷移の設計の穴** (ビジネスロジックの脆弱性)。
- 対策: 形式検証、数の上限、トークンバケットによる試行制限と失敗時の遅延、3 回失敗で切断、
  パスワードの定数時間比較、未結び付けの端末には保存済みパスワードとの一致を必須に、
  新しい資格情報は REGISTER 成功まで「仮」とし、拒否が続けば取り消す。
  - `relay/internal/session/session.go` (`bindAccount`), `group.go`, `limits.go`, `security_test.go`
- 位置づけ: CWE-307 (試行回数の制限不備), CWE-770 (無制限なリソース割り当て), CWE-208 (タイミングの差),
  OWASP API4:2023 (Unrestricted Resource Consumption)。
- レビューで見つかった二次的な問題: 取り消し処理と再接続が同時に走るとロールバックが漏れる**競合状態**
  (CWE-362)。また、取り消しを 15 秒で行う初版は「アプリを先に変えて Asterisk を後で変える」正規の手順を
  壊した。**セキュリティ対策が可用性を削る**典型例で、最終的に「拒否 3 回かつ 2 分継続」に緩めた。

### 3.3 relay: 運用・デプロイ

**#37 cloudflared が `latest`、コンテナの権限が無制限、危険な設定の組み合わせを許していた**
- サプライチェーン: `latest` は中身が勝手に変わる。全トラフィックを通すコネクタなので、バージョンを固定し
  更新を意図した作業にする (digest 固定はさらに強いが、セキュリティ更新が止まるトレードオフ)。
- コンテナの最小権限: `read_only`, `cap_drop: [ALL]`, `no-new-privileges` (CIS Docker Benchmark の定番)。
- 付随で見つかった露出: cloudflared はコンテナ内では metrics を `0.0.0.0` で開くので、host ネットワークだと
  LAN に `/metrics` や `/debug/pprof` が見えていた (CWE-200)。トークンを argv で渡すと `ps` で見える (CWE-214)。
- **安全な既定値 (secure by default)**: 共有トークン認証 (`AUTH_MODE=token`) を loopback 以外で待ち受ける
  設定は起動エラーにした。事故の起きやすい組み合わせは、設定ミスとして起動時に止める。
  - `relay/internal/config/config.go`, `deploy/docker-compose.yml`

**文書で対応したもの (#33 #34 #35 #38 #39)**
- #33 状態ファイルに SIP パスワードが平文: REGISTER に平文が要る。同じホストに鍵を置く暗号化は
  見かけだけ (鍵と暗号文が同じ場所にある) なので、ファイル権限と運用で守ると判断した。
- #34 Cloudflare の edge で TLS が終端する = Cloudflare には中身が見える。「誰を信頼しているか」の明示。
- #38 着信 push の中身に発信者番号が入り Google を経由する。**データ最小化** (privacy by design) の観点。
- #39 セキュリティモデル文書 → `docs/SECURITY.md` を新設。**残存リスクを書いておく**こと自体が対策の一部。

### 3.4 Android アプリ

**#41 debug / probe ビルドの exported receiver を任意のアプリから叩けた**
- 攻撃: 同じ端末の悪意あるアプリが relay URL を自分のサーバに書き換えて再起動させると、アプリが
  CF Access の資格情報と SIP パスワードをそのサーバへ送る。着信応答や発信も操作できた。
- 対策: receiver に `android:permission="android.permission.DUMP"` を要求。adb shell (DUMP を持つ) からは
  届き、第三者アプリは取得できない。
- 位置づけ: CWE-926 (Android コンポーネントの不適切な公開)、MASVS-PLATFORM-1 (IPC を安全に使う)。
- 学びどころ: 「debug ビルドだから大丈夫」は、debug ビルドが実運用機に入った瞬間に崩れる。
  実機での試験では、**同じアプリの uid から送ると権限チェックが免除される**ため、それで「届いた」のは
  無効な試験だった。別アプリ (別 uid) から送って初めて Permission Denial を確認できた。**テストの前提を疑う**。

**#43 平文 (ws:// http://) を黙って受け付けていた / #44 証明書ピンニングが無い**
- 対策: network_security_config で release は平文禁止・system CA のみ、debug は localhost のみ許可。
  設定画面で平文 URL を保存前に拒否。
- 位置づけ: CWE-319 (平文通信), MASVS-NETWORK-1。
- #44 は**直さない判断**: ピンニング (MASVS-NETWORK-2) は、証明書が自動更新・CA 変更される Cloudflare では、
  更新のたびに全端末が繋がらなくなるリスクの方が大きい。ユーザー追加の CA は既定で信頼されないので、
  中間者攻撃の主経路は既に塞がっている。**全部の推奨を機械的に入れるのがベストプラクティスではない**。

**#42 暗号化ストアが壊れると黙って平文に切り替えていた / #48 バックアップ**
- 対策の第 1 版は「失敗したら鍵とファイルを消して作り直す」だったが、レビューで
  **Keystore の一時的な障害でも設定を消してしまう後退** (可用性の破壊) と判明した。最終版は:
  - 例外を原因で分類 (一時障害 / 破損)。一時障害は消さず、保存も拒否する (平文にも書かない)。
  - 破損は別々の起動で 2 回続いたときだけ確定し、削除ではなく退避 (`.broken-*`) して作り直す。
  - 設定変更を「読み込み→変更→書き込み」の原子的な `update()` に一本化 (既定値で上書きする競合を防ぐ)。
  - バックアップと端末間移行の対象から外す (MASVS-STORAGE-2)。
  - `android/.../BridgeConfig.kt`, `EncStoreResolver.kt`, `PrefsFailure.kt` と各テスト
- 位置づけ: CWE-636 (安全に失敗しない), MASVS-STORAGE-1。
- 学びどころ: 「フェイルセキュア」は「失敗したら全部消す」ではない。**機密性・完全性・可用性の釣り合い**を
  取り、失敗の種類を見分けて扱う。5 回のレビューのうち 4 回はこの部分だった。

**#46 未使用の権限 / #47 ログに通話メタデータ / #45 ロック画面の番号表示**
- #46: 使わない権限は宣言しない (最小権限)。
- #47: release ではログの番号・内線・URL を伏せ字にする (CWE-532, MASVS-STORAGE-2)。
- #45: 電話アプリとして標準的な挙動なので**受容**した (リスク受容の記録)。

## 4. 横断的な学び

1. **暗黙の信頼を列挙する**: 今回の問題の多くは「LAN だから」「debug だから」「署名が正しいから」
   「自称の ID だから」という暗黙の信頼。信頼境界ごとに「何を根拠に信じているか」を書き出すと見つかる。
2. **対策は可用性を壊しうる**: データ消失 (#42 初版)、正規手順の締め出し (#30 初版)。
   セキュリティ修正にも回帰試験と実機試験が要る。
3. **検証 → 実装 → 敵対的レビュー → 実機 E2E** の順: 監査の指摘を鵜呑みにせず、まず PoC で実在を確認した
   (#44 は脆弱性ではないと判定)。レビューは実装者と別の目で「どう壊れるか」を探した。
4. **認証と送信元フィルタは違う**: 偽装できる情報 (UDP の送信元、自称の ID) は、多層防御の 1 層にはなるが
   認証の代わりにはならない。
5. **共有秘密は帰属を失わせる**: 1 本の token を全員で使うと、誰がやったか分からず、1 本の漏洩で全員が破られ、
   端末単位の失効もできない。
6. **ライブラリの既定値を確認する**: JWT の exp、sipgo の URI 直列化 (エスケープしない)、
   cloudflared の metrics の待ち受けアドレス、いずれも既定のままだと危険だった。
7. **直さない判断も設計**: #44 #45 のように、理由を付けて受容し、残存リスク表に書く。

## 5. 運用者が次にやること (一般論)

- Service Token を端末ごとに発行し、`DEVICE_BINDING` を `warn` で様子を見てから `enforce` に。
- 既定アカウント (`SIP_USER`) を使わない (漏洩トークンだけで発信できるため)。
- Asterisk の relay 用内線の発信 context を、必要な宛先だけに絞る (トールフロード対策)。
- relay と Asterisk を VLAN などで他の機器から分離する。
- 端末紛失時の失効手順を把握しておく (`docs/SECURITY.md` §7)。

## 6. 理解度チェック・壁打ち用の問い

1. SIP の送信元 IP フィルタを入れたのに「これは認証ではない」と言うのはなぜか。では何があれば認証と言えるか。
